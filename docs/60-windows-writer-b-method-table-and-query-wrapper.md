## 1. Writer B — це слот у таблиці методів

`0x18036bb70` інсталює таблицю методів у приймач `rcx` (`ev_77236019…`). Перший запис:

```
0x18036bb70: lea rax,[0x18036d300]
0x18036bb77: mov [rcx+0x6c98],rax
```

Отже Writer B — це метод `+0x6c98`, як і передбачалося в `docs/56`, але тепер це `statically proven` (`ev_77236019…`). Інсталятор пише неперервний набір слотів від `+0x6c98` до `+0x7190`.

Сам Writer B `0x18036d300` (`ev_6194d447…`) має `rbx=arg2` (приймач/device), `rdi=arg1` (джерело). На початку він обнуляє 0x800-байтний локальний блок, викликає той самий інсталятор `0x18036bb70` на `rbx`, а потім копіює поля з `rdi` в `rbx`. Тобто він не просто записує UUID — він ще й інсталює таблицю методів на приймачі.

## 2. Джерельний діапазон Writer B

У [`docs/59`](59-windows-adapter-private-field-to-uuid-writers.md) вже зафіксовано копію 16 байт `[rdi+0x481] → [rbx+0xc27]`, прапорець `[rbx+0x5e49] |= 1` і сусідні байти. Новий факт (`ev_c1db24ba…`): єдине входження `+0x470` у Writer B — `0x18036d65a: movzx eax, byte [rdi+0x470]`. Разом із `[rdi+0x471]` і `[rdi+0x481]` це неперервний 17-байтний діапазон, який починається з `rdi+0x470`.

**Статус**: `statically proven` для читання цього діапазону. **UNPROVEN**: хто саме створює об'єкт-джерело `rdi` і чи містить він дані з нормалізованого буфера адаптера з `docs/59`. Прямий виклик Writer B відсутній; методи викликаються через слоти таблиці, тому `axt` бачить лише DATA-посилання.

## 3. Хто будує таблицю методів

`axt @ 0x18036f270` (`ev_d24d62a2…`) показує єдиного прямого caller — `0x18036c734` усередині `0x18036c430` (`ev_5f46cac2…`). Там таблиця будується в циклі: `rcx=[var_7f8h]`, `rdx=&var_7d8h`, `r8d=count-1`, `r9d=r14b`. Direct callers `0x18036c430` — `0x18036ca62` і `0x18036cbe1` (`ev_8e9199b0…`), обидва в безіменних областях.

Це звужує походження таблиці, але не дає змоги стверджувати, що вихідний об'єкт `rdi` Writer B є тим самим об'єктом `0x28f8` або буфером адаптера з `docs/59`. Зв'язок лишається **UNPROVEN**.

## 4. Обгортка `D3DKMTQueryAdapterInfo` уточнена

`0x1800050c0` (`ev_a85e80f7…`) формує 0x14-байтний блок:

| Зміщення блоку | Джерело |
|---|---|
| `+0x00` | `ecx` |
| `+0x04` | `edx` |
| `+0x08` | `r8` (вказівник буфера) |
| `+0x0c` | `r9d` (тип запиту) |
| `+0x10` | `0` |

Потім `rcx=&block`, `call [0x18008d088]` — `D3DKMTQueryAdapterInfo`, встановлений у `docs/58`. У `docs/59` зафіксовано `r9d=0xc115` для виклику з `0x18000590e`. Висновок: `0xc115` — справді тип запиту в цьому блоці, а буфер адаптера `r15` передається як `r8`.

## 5. Хто викликає Writer A

`axt @ 0x180409010` (`ev_eaa0b508…`) дає єдиного прямого caller — `0x18040a09b` усередині `0x180409f50` (`ev_9b7f2490…`). Перед викликом відбувається фільтр class-констант: `0xc6c0`, `0xc1c0`, `0xb0c0`, `0xb1c0`, `0xc0c0`, `0xc3c0`, `0xc5c0`, `0xc7c0`, `0xc9c0`, `0xcbc0`, `0xcdc0`, `0xcec0`. Після успіху `dword [arg2+0x08]` збільшується. `arg2` зберігається в `rsi`.

## 6. Глобальна таблиця пристроїв

Пошук `[0x182002520]` у Writer A (`ev_9cf87d21…`) дав порожній результат: `UNPROVEN` щодо того, хто зберігає заповнені device-об'єкти в таблицю, яку читає `cuDeviceGetUuid`. `axt @ 0x180048780` (`ev_3ac98692…`) показує лише відомі шляхи `cuDeviceGetUuid` — `0x18028039a`, `0x1802804d7`, `0x18021ee9a`, `0x18021efd7` і два тонкі thunk-и; нових producer-ів це не додає.
