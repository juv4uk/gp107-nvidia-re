# 46 — E1: готовий рецепт read-only трасування `cuCtxCreate…cuLaunchKernel`

## Мета й статус

[`42`](42-local-toolchain-and-remaining-targets.md) призначає для E1 інструменти:
власний LD_PRELOAD-shim і `strace`. Це план, а не команда. Тут — команди, які
можна виконати, і формат таблиці, яку вони мають дати.

Смуга **B**: спостереження викликів shipped-стеку. Це не аналіз бінарника, тому
ліцензійний gate з [`42`](42-local-toolchain-and-remaining-targets.md) §1 не
потрібен. Нічого з vendor-коду не копіюється і не декомпілюється.

Статусів у [`05`](05-gp107-capability-matrix.md) цей документ не змінює.

## Що саме треба отримати

Таблицю, у якій кожен рядок — один виклик, і кожен стовпець — факт, а не
здогад:

| # | виклик | напрям | розмір | імʼя константи | статус |
|---|---|---|---|---|---|
| 1 | `ioctl(/dev/nvidiactl, 0xc90046c8, ...)` | RW | 72 | `NV_ESC_CARD_INFO` | 0 |
| 2 | `openat("/dev/nvidia0", ...)` | — | — | — | 3 |

Невідомий request **не** викидається: він лишається рядком зі статусом
`UNPROVEN` і номером. Саме так [`05`](05-gp107-capability-matrix.md) відрізняє
«не спостерігали» від «не існує».

## Крок 1 — мінімальна програма, яку трасуємо

Не потрібен CUDA Toolkit. Потрібне навантаження, яке справді проходить шлях
`context → stream → memcpy → kernel`. Мінімум, який це робить, — будь-який
наявний приклад із `cuda-samples` або власна програма на `libcuda` через
`dlopen`. Важливо, щоб вона **завершувалась**, а не висіла в очікуванні.

## Крок 2 — два незалежні спостерігачі

`strace` як перший свідок:

```sh
strace -f -yy -e trace=ioctl,mmap,openat,close \
  -o /tmp/e1-strace.log \
  ./your-cuda-program
```

`bpftrace` як другий, незалежний — він бачить ті самі виклики з іншого боку й
не залежить від того, чи програма не форкається:

```sh
sudo bpftrace -e '
  tracepoint:syscalls:sys_enter_ioctl
  /comm == "your-cuda-prog"/
  { printf("%s fd=%d req=0x%x\n", comm, args->fd, args->cmd); }
' -o /tmp/e1-bpftrace.log
```

Критерій green із [`42`](42-local-toolchain-and-remaining-targets.md): **два
прогони дають однакову таблицю**. Один прогін нічого не доводить — порядок
викликів може залежати від кешу.

## Крок 3 — назви констант

Номери самі по собі нічого не кажуть. Декодер уже є:

```sh
./scripts/decode_ioctl.py < /tmp/e1-strace.log
```

Він приймає і голі hex-номери, і рядки `strace`. Якщо номер невідомий, він так
і скаже — і це правильний результат, а не привід вигадати назву.

Таблицю з Кроку 4 не треба складати руками — її будує той самий інструментарій:

```sh
./scripts/e1-trace-table.py /tmp/e1-run1.log /tmp/e1-run2.log
```

Він друкує Markdown із трьома частинами, які навмисно не змішуються: декодовані
запити з `dir/magic/nr/size` і кількостями, **окрему** таблицю нерозпізнаних
(`UNPROVEN`), і секцію стабільності — що саме відрізняється між двома прогонами.
`--strict` валить прогін, якщо хоч один request лишився безіменним у будь-якому
з переданих логів — це негативна половина критерію E1. Таблиця
`UNPROVEN` агрегує кількості з усіх переданих прогонів. `--require-stable`
валить прогін, якщо два прогони побачили різні набори запитів — це його
позитивна половина, і саме вона перетворює «два прогони схожі» з оцінки на
перевірку.

Один прогін усе ще нічого не доводить — скрипт лише показує різницю, а рішення
про стабільність лишається за тим, хто читає таблицю.

## Крок 4 — що робити з таблицею

1. Кожен новий request — окремий рядок у звіті E1 зі статусом `UNPROVEN`,
   доки не підтверджений другим прогоном.
2. Кожен підтверджений request переноситься в
   [`ioctl-map.md`](ioctl-map.md) лише з посиланням на лог, у якому він
   спостерігався.
3. Розмір аргументу з `strace` — це розмір **переданого** буфера, не довжина
   структури в заголовку. Не плутати.

## Чого це не доводить

- **Не доводить семантику.** «`ioctl` прийнято зі статусом 0» означає, що
  драйвер не відмовив, а не що структура заповнена так, як ви думаєте.
- **Не доводить, що це єдиний шлях.** Інший ICD або інша версія драйвера може
  робити інший набір викликів.
- **Не дає права на writable BAR0.** Жоден крок вище не відкриває `resource0`
  на запис, і E1 цього не потребує.
- **Не замінює E2.** Порядок викликів — не те саме, що lifecycle RM-обʼєктів:
  для E2 потрібен власний зонд, який сам створює й звільняє обʼєкти.

## Чому E1 першим

Він не потребує root, не потребує MMIO, не потребує ліцензійного clearance і
не може нічого зламати: він лише фіксує те, що вже відбувається на цій машині.
Найдешевший крок, який дає найбільше для наступних.
