## 1. Алокатор `0x180204930`

`fcn.180204930(rcx=state, rdx=source, r8=out)` (`ev_8fb0d26…`):

| Адреса | Дія |
|---|---|
| `0x180204948`/`0x180204959` | `ecx=0x73b8`, виклик алокатора; `0x18020496f`–`0x18020497a` обнулює `0x73b8` байт (`ev_0d5c91…`) |
| `0x180204a74`/`0x180204a7c` | `ecx=[state]`, `inc [state]` — ordinal об'єкта |
| `0x180204a8e`–`0x180204aa0` | `[state+0x2c8] = object`, `[object+0x73a8] = former head` — вставка в голову списку (`ev_ddcf47…`, `ev_5e4e16…`) |
| `0x180204ac3`–`0x180204afe` | гілка для непустого списку: зв'язки через `+0x2d0`, `+0x73a8` і `+0x73b0` (`ev_7e8625…`) |
| `0x180204b19` | `[state+0x2d0] = object` — оновлення хвоста списку |
| `0x180205329` | `[r8] = object` — повернення об'єкта через out-параметр (`ev_8fb0d26…`) |

Це **той самий** список, який publisher `0x180208bf0` читає через `[state+0x2c8]` і далі `[node+0x73a8]` (`ev_5e4e16…`, `ev_7e8625…`). Отже об'єкти, які публікуються в таблицю `cuDeviceGetUuid`, створюються саме цим алокатором. **Статус: `statically proven`**.

## 2. Знайдено виклик Writer B

Раніше Writer B мав лише DATA-xrefs через таблицю методів. Тепер у самому алокаторі (`ev_ddcf47…`):

```
0x180204b20  call qword [rdi]          ; source-колбек з arg2
0x180204b26  mov rcx, rdi              ; arg1 = source
0x180204b29  mov [rax+0x72c8], rbx     ; зворотний вказівник на state
0x180204b34  mov rdx, rax              ; arg2 = щойно створений object
0x180204b37  call qword [rax+0x6c98]   ; Writer B
```

Слот `+0x6c98` ідентифіковано ще в `docs/60` як Writer B, інстальований `0x18036bb70`. Тому це **не новий метод**, а саме опосередкований виклик Writer B на новоствореному device-об'єкті; окремо `0x180204b19` оновлює хвіст списку. **Статус: `statically proven`** для indirect call.

Будівельник таблиці методів `0x18036f270` із `docs/60` і сам викликає `0x180204930`: `0x18036f652` — `rcx=[var_500h]`, `0x18036f657` — `r8=&var_508h`, `0x18036f65c` — `rdx=&var_4e8h`, `0x18036f667` — `call`, далі `0x18036f695`/`0x18036f69a` використовують повернений об'єкт як `[rax+0x72e0]=rcx` (`ev_0aaf2d2…`). У тій самій функції `0x18036f2d2` посилається на `0x18036bb70` (`ev_acf7a79…`). Прямі callers алокатора — `0x180024df6`, `jmp` на `0x180026a80`, `0x18036f667` і `0x180409608` (`ev_707fc53…`). **Статус: `statically proven`** для участі того ж алокатора в обох шляхах.

## 3. Writer A бере об'єкт із того ж алокатора

У Writer A `var_9b0h` — не звичайний локальний, а out-параметр (`ev_8f8e4e7…`, `ev_b8d40ee…`):

```
0x1804095f7  mov rcx, [var_980h]       ; arg1 / state
0x1804095fc  lea r8,  [var_9b0h]       ; out
0x180409608  call 0x180204930
0x180409615  mov rax, [var_9b0h]       ; повернений object
0x1804096ef  movups [rax+0xc06], xmm0  ; 16 байт UUID-поля
```

Тобто об'єкт, у який Writer A пише `+0xc06`, і об'єкт, який алокатор вставляє у список і публікує таблиця, — продукти одного й того самого `0x180204930` з тією самою розкладкою `+0x2c8`/`+0x73a8`/`+0x5e49`. **Статус: `statically proven`** для спільного алокатора й розкладки.

## 4. Що саме знято, а що ні

| Твердження з `docs/61` | Новий статус |
|---|---|
| Вузли таблиці мають спільну з Writer A/B розкладку | `statically proven`, тепер через спільний алокатор |
| Хто викликає Writer B | `statically proven`: `[object+0x6c98]` усередині `0x180204930` |
| Тотожність об'єкта Writer A/B і вузла таблиці | `statically proven` на рівні алокатора й списку; **UNPROVEN** для того, що state-вказівник Writer A є тим самим глобальним `0x182004420`, який використовує publisher |
| Хто створює перший вузол | частково знято: алокатор відомий; хто вперше викликає publisher — два шляхи з `docs/61` |
| Походження 16 байт, `BDF ↔ RM gpu_id` | `UNPROVEN` |
| Виконання на цій машині | `NOT RUN` |

Writer A отримує state як `arg1`; у безпосередньому caller `0x180409f50` це `r14 = [arg2]` (`ev_2bd459e…`), а сам `0x180409f50` викликається через `[iface+0xc0]` з контекстом (`ev_774e875…`, `ev_0dc3219…`). Прямої рівності з `0x182004420` у Writer A немає (`ev_41da992…` — порожній результат цільового пошуку), а xrefs глобального state не ведуть до цього контексту (`ev_f4896ba…`). Тому global state identity чесно лишається `UNPROVEN`.

## 5. Межі доказів

Ghidra-xrefs не заявляються: 34 MB DLL двічі не завершив аналіз (`provider_timeout`). `axt` виконувався з `aaa` у тій самій команді. Деякі `pd`-вікна починалися посеред інструкції; усі цитовані адреси підтверджено або `pdf` після `af`, або вирівняними `pd`-вікнами. `bin_file_strings`-warnings у stderr не спростовують наведені CALL/DATA-xrefs. Не виконувалося жодного `cuInit`, `cuDeviceGetUuid`, CUDA/Vulkan/OpenGL init, RM/UVM/D3DKMT ioctl, GPU submit, MMIO, firmware, reboot, tag чи release.
